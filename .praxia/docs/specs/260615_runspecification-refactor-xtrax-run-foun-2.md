# Brainstorm: RunSpecification refactor + xtrax.run foundation: is the epic spec complete, correctly sequenced, and missing anything?

## Problem Frame
Fixed constraints (cannot change): (1) sidechain_conditioning + fixed_mask go to RunSpecification BASE via inheritance — not duplicated to InspectionSpec. (2) xtrax.run is in scope immediately — multiple downstream projects build against it now. (3) Fuse/Tap/Sink/AxisBoundary land in xtrax/stages/boundaries.py — not a new top-level package. (4) output_h5_path stays per-subclass for now (deprecated bridge). (5) chain_mask fix must use _broadcast_per_structure, not raw spec.fixed_mask. (6) FeatureNoiseBundle groups feature type + levels + mode + noise_fn. (7) Logical grouping stays one level deep. Negotiable: exact field names (tile_granularity vs granularity), the precise shape of InputResolver's type parameters, whether SinkConfig is per-subclass or a shared SinkSpec, the FuseFn reconciliation strategy, and the double-fire guard implementation approach.

## Idea Pool
- [ai] AREA 1 — H4 FuseFn reconciliation is underspecified. The current spec says "reconcile with FuseFn already in stages/protocols.py" but gives no concrete API. FuseFn in protocols.py is likely typed as a callable — the reconciliation could mean: (a) Fuse becomes a class that wraps FuseFn, making FuseFn the underlying protocol and Fuse the named boundary marker; or (b) FuseFn is replaced entirely by Fuse with __call__ defined on the class. The spec should state which object is the primary API surface and which is the alias/shim.
- [ai] AREA 1 — Alternative FuseFn reconciliation: keep FuseFn as the Protocol (callable type), make Fuse a TypeAlias for FuseFn, and let Tap/Sink be separate protocols with __call__ signatures that narrow the return type. AxisBoundary becomes a Union[Fuse, Tap, Sink]. This means protocols.py keeps FuseFn but re-exports it from boundaries.py — no deletion, no shim.
- [ai] AREA 1 — Gap: the spec does not specify what happens to FuseFn in stages/protocols.py after H4. If it stays as a separate definition and boundaries.py defines Fuse independently, aminx gets two parallel objects at import time. The spec needs an explicit "FuseFn deprecated after H4, import from xtrax.stages.boundaries" deprecation notice with a timeline, or an immediate alias with __all__ control.
- [ai] AREA 2 — FeatureNoiseBundle as a dataclass or NamedTuple rather than an eqx.Module. If noise_fn is a JAX-traceable callable, it must be a leaf in the PyTree, which pushes toward eqx.Module. But if FeatureNoiseBundle is only used at construction time (not passed through jit boundaries), a plain dataclass is simpler and avoids the eqx overhead. The spec should state whether FeatureNoiseBundle participates in jit or is a pure config object.
- [ai] AREA 2 — Alternative: FeatureNoiseBundle as a TypedDict instead of a class, allowing JSON/TOML serialization without a custom encoder. The list[FeatureNoiseBundle] would then be list[dict] at the wire level, validated at RunSpec construction. This trades static type safety for simpler config file round-trips — relevant if RunSpec is loaded from YAML/TOML.
- [ai] AREA 2 — Gap: the spec does not address how the 8 scattered noise fields map to FeatureNoiseBundle entries. A field-to-bundle mapping table is needed (similar to the R7-1 AxisSpec gate) to ensure no field is dropped. Without it, a sprint implementer will make judgment calls about which old fields correspond to which bundle attributes.
- [ai] AREA 3 — SinkConfig per-subclass as a bridge is correct if the goal is backward compatibility. But it creates a heterogeneous type: SamplingRunSpec.sink = SamplingSinkConfig, InspectionRunSpec.sink = InspectionSinkConfig. Callers that want to write generic code over RunSpec cannot do so without isinstance dispatch. A shared SinkSpec base with subclass-specific fields in a tagged union (via discriminated union or Protocol) would allow generic runners.
- [ai] AREA 3 — Alternative: SinkSpec lands directly in RS-6 as the canonical type, with output_h5_path as a deprecated Optional[str] field on SinkSpec itself (not on the RunSpec subclass). This collapses the per-subclass SinkConfig into a single object and makes the deprecation path explicit in one place. Downside: requires all subclasses to update their __init__ in RS-6 rather than deferring to RS-7.
- [ai] AREA 4 — Missing dependency: H4 (promote boundaries) ships in sprint 260618, but R6-4 (FuseFn/Fuse unification in xtrax.stages) is listed under RS-6. If H4 ships first and creates boundaries.py with Fuse as a standalone class, and then R6-4 tries to unify it with FuseFn from protocols.py, R6-4 is doing cleanup that should have been part of H4. The reconciliation step logically belongs in H4, not deferred to RS-6. This is a sequencing gap.
- [ai] AREA 4 — Missing item: there is no specified test coverage gate for H1 (moving sidechain_conditioning + fixed_mask to BASE). If InspectionSpec previously did not have these fields and SamplingSpec did, moving them to BASE changes the InspectionSpec public surface. Any test that constructs InspectionSpec without these fields will still pass, but any code that does `isinstance(spec, SamplingSpec)` to gate on sidechain_conditioning will now get the field on InspectionSpec too — a silent behavior change. A test asserting the field IS on BASE and NOT only on SamplingSpec is needed.
- [ai] AREA 4 — Missing item: no deprecation/migration shim is specified for the AveragingMode shim in R6-3. The spec says "AveragingMode shim" but does not specify how long the shim lives, whether it raises DeprecationWarning, and in which sprint it gets removed. Without a removal timeline, shims accumulate.
- [ai] AREA 4 — Missing item: R6-1 creates InputResolver as a Protocol parametrized over Spec+Bundle. R6-2 introduces the grouping sub-configs. But if ModelConfig and ResourceConfig are sub-configs of RunSpec, and InputResolver receives a RunSpec, InputResolver callers must know the internal sub-config layout. The spec does not address whether InputResolver sees RunSpec directly or only sees the resolved sub-configs. This is a design surface that will force revision if left unspecified.
- [ai] AREA 4 — Missing item: the spec does not address what happens at the xtrax/run/__init__.py public surface. Which names are exported? RunSpec, SinkSpec, SinkFactory, InputResolver, AggregationFn, DecodeFn, NoiseFn — all of these? Or does xtrax.run expose only the protocols and xtrax.run.spec exposes RunSpec? The public API boundary of the new module is unspecified.
- [ai] AREA 5 — tile_granularity naming conflict: xtrax already has a field or concept called granularity. Using tile_granularity as the new AxisSpec field name avoids the collision but creates an asymmetry — prolix uses one name, xtrax uses a prefixed variant. An alternative is to use axis_granularity (scoped to the axis context) rather than tile_granularity (which implies tiling semantics specifically). If the field controls vmap tiling grain, tile_granularity is accurate; if it controls any axis subdivision, axis_granularity is more general.
- [ai] AREA 5 — The R7-1 gate (three-column field mapping table) is listed before any code, which is correct. But the gate should also explicitly require resolving the tile_granularity vs granularity naming conflict as a deliverable of R7-1, not leaving it to R7-2. If R7-2 ships with the wrong name, it touches AxisSpec's public API a second time in a follow-on sprint, which is expensive.
- [ai] AREA 6 — RuntimeBundle concrete shape: it should contain at minimum: (a) the resolved model (post-load, post-jit), (b) decoded tokenizer or alphabet, (c) device placement info, (d) RNG key or seed state. The spec mentions RuntimeBundle in the context of InputResolver but does not enumerate its fields. Without a concrete field list, InputResolver implementors in multiple downstream projects will diverge on what they expect from the bundle.
- [ai] AREA 6 — RuntimeBundle as an eqx.Module vs a plain dataclass: if the model field is an eqx.Module, RuntimeBundle must also be an eqx.Module (or at least PyTree-aware) for jit compatibility. If RuntimeBundle is a plain dataclass holding an eqx.Module, it becomes an opaque leaf — callers cannot vmap over it. The spec must specify whether RuntimeBundle crosses jit boundaries or is always constructed outside jit and passed in once.
- [ai] AREA 6 — Alternative RuntimeBundle: split into StaticBundle (non-JAX config: tokenizer, device config, paths) and ModelBundle (eqx.Module holding model weights). InputResolver receives StaticBundle; the runner holds ModelBundle separately and passes model as a first-class argument to the stage functions. This avoids PyTree contamination of the resolver.
- [ai] AREA 7 — InputResolver parametrized over Spec+Bundle: the current framing implies InputResolver[Spec, Bundle] → Inputs. The risk is that Spec and Bundle are concrete types that differ per run mode, making InputResolver a generic Protocol with two TypeVars. Generic Protocols in Python require explicit __class_getitem__ and break mypy's structural checking unless the TypeVars are covariant. A simpler alternative: InputResolver is not parametrized — it takes Any for spec and bundle at the Protocol level, and concrete implementations use overloads or runtime dispatch. This sacrifices static typing at the protocol boundary but avoids the generic Protocol complexity.
- [ai] AREA 7 — Alternative InputResolver shape: instead of parametrizing over both Spec and Bundle, make InputResolver a callable protocol that takes (spec: RunSpec, bundle: RuntimeBundle) → FeatureBatch, where RunSpec and RuntimeBundle are the base types. Subclass-specific resolvers are registered via a dispatch registry (singledispatch on spec type). This is simpler to type-check and matches how JAX dispatch patterns typically work.
- [ai] AREA 7 — Gap: the spec does not state the return type of InputResolver. "Inputs" is mentioned contextually but not defined. Is it a FeatureBatch? A dict[str, Array]? A named eqx.Module? The return type of InputResolver is the input contract for every stage function downstream. If it is unspecified, stage functions will independently define their expected input shape, creating divergence.
- [ai] AREA 8 — _sync_run_spec guard-flag approach: setting a boolean flag on the object to prevent double-fire is fragile in two ways. (a) If RunSpecification is frozen (eqx.Module is immutable), you cannot set a flag on self — you need to store it externally or use a mutable wrapper. (b) If the spec is copied (e.g., eqx.tree_at), the flag resets. A cached property approach (using functools.cached_property or a __post_init__ sentinel value) is safer for immutable objects.
- [ai] AREA 8 — Alternative to guard-flag: make _sync_run_spec idempotent rather than guarded. If the sync operation is deterministic and cheap, calling it twice produces the same result, so no guard is needed. The spec should state whether _sync_run_spec has side effects (e.g., sets fields on a mutable store) or is a pure computation. If it has side effects, the guard is needed. If it is pure, idempotency eliminates the guard entirely and the H3 task becomes "make sync idempotent" rather than "add guard".
- [ai] AREA 8 — Gap: the spec says _sync_run_spec double-fires but does not specify WHEN it fires twice. Is it called in __init__ and then again in a property getter? Is it triggered by two callers hitting the same spec? Without knowing the trigger, the guard placement is ambiguous — you might guard in __init__, in the method itself, or at the call site. The spec needs a one-line description of the double-fire trigger before the fix can be correctly designed.
- [ai] CROSS-CUTTING — Sequencing risk: RS-6 (R6-1) creates xtrax/run/RunSpec as an eqx.Module. RS-7 (R7-5) migrates *_batch_size fields to *_axis: AxisSpec. If RunSpec is built in RS-6 with *_batch_size fields, then RS-7 changes those field names, every downstream caller that built against RS-6 must update. Consider whether the AxisSpec migration belongs in RS-6 (so RunSpec ships with final field names) rather than in RS-7 (which creates a second API churn for the same fields).
- [ai] CROSS-CUTTING — Missing: no integration test spec for the full RunSpec → InputResolver → Stage → Sink pipeline. The spec defines each component in isolation. Without an end-to-end integration test defined as a deliverable of RS-6, it is possible to ship all components with individually passing unit tests but a broken pipeline due to interface mismatches between them.
- [ai] CROSS-CUTTING — Missing: the spec does not address versioning or __version__ for the xtrax.run module. Since multiple projects build against it immediately, any breaking change in RS-7 needs a version bump signal. Even a simple CHANGELOG entry or a __schema_version__ on RunSpec would allow downstream projects to guard on the version rather than catching AttributeError.
- [ai] CROSS-CUTTING — H2 (chain_mask fix) uses _broadcast_per_structure helper. The spec says "take complement (1.0 - fixed_mask_np)" but does not state what type fixed_mask_np is at the point of complement. If it is a JAX array, the complement is correct. If it is a numpy array with dtype uint8 (common for mask fields), (1.0 - fixed_mask_np) silently produces a float result from an int array, which may cause downstream dtype mismatches in the chain_mask accumulation. The spec should explicitly state the expected dtype of fixed_mask_np before the complement operation.
- [ai] AREA 4 — Missing: no spec for how aminx re-exports from xtrax.stages.boundaries.py after H4. The spec says "aminx re-exports" but does not specify the re-export file. If aminx/types/boundaries.py becomes the re-export shim, it must be emptied of definitions and replaced with `from xtrax.stages.boundaries import ...`. If there is no shim and aminx types are deleted, all existing aminx callers that import from aminx.types.boundaries break immediately. The re-export path is underspecified.
- [user] 29 ideas recorded across all 8 focus areas plus 5 cross-cutting concerns. The major clusters are: (1) H4 FuseFn reconciliation is underspecified — the spec needs to name which object is primary and what happens to FuseFn in protocols.py after H4, and R6-4 should likely merge into H4. (2) FeatureNoiseBundle needs a field-to-bundle mapping table analogous to the R7-1 AxisSpec gate, and needs to specify whether it crosses jit boundaries (eqx.Module vs dataclass). (4) Multiple missing items: aminx re-export path for H4, AveragingMode shim removal timeline, xtrax/run public API surface (__all__), InputResolver return type, RuntimeBundle concrete fields, integration test gate for RS-6, and the double-fire trigger description for H3. (5) RS-7 should lock the tile_granularity naming in R7-1 gate, not defer to R7-2.
